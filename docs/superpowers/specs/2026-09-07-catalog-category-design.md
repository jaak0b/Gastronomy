# Categories become a thing the admin creates

Date: 2026-09-07

## Why

A category exists today only as a word typed onto every article, so it cannot be renamed, removed,
reordered or coloured, and a typo silently creates a second category nobody wanted. The phone is
about to make categories the main way a waiter navigates, as large coloured buttons in an order the
admin chooses, and a navigation element needs identity, order and colour. The schema is still free to
change because nothing is installed at the fire department yet.

This change covers the laptop only. The phone keeps the screens it has today; its redesign is the
next piece of work and builds on what this one creates.

## What the admin sees

No new tab. The Artikel page keeps its shape, and the category headings it already draws gain their
own controls: the colour, rename, move up, move down, and switch off. A "Neue Kategorie" button sits
beside "Neuer Artikel". In the article dialog the category becomes a pick from the list, with the
option to create one on the spot.

## Rules

- A category is switched off, never deleted, like articles, stations and waiters.
- Switching a category off is refused while it still holds active articles.
- Reactivating an article whose category is switched off is refused. Without this the forbidden state
  sneaks in through the back door: switch everything off, then reactivate one article.
- A category name is unique, compared case insensitively.
- The colour is a free choice. The app derives the lettering colour from the colour's brightness, so
  no choice can produce an unreadable button.
- The category's position decides the order everywhere. The two derivations that exist today, the
  server's lowest article position and the phone's alphabetical sort, both go.

## Database

New table `CatalogCategories`:

| Column | Type | Constraints |
|---|---|---|
| `Id` | TEXT | primary key, Guid, never generated by the store |
| `Name` | TEXT | required, max 200, unique, case insensitive |
| `ColourHex` | TEXT | required, exactly `#RRGGBB` |
| `SortOrder` | INTEGER | required |
| `IsActive` | INTEGER | required |

Changed table `CatalogItems`:

| Change | Detail |
|---|---|
| removed | `CategoryName` TEXT(40) NOT NULL |
| added | `CategoryId` TEXT NOT NULL, foreign key to `CatalogCategories(Id)`, delete restricted |
| added | index `IX_CatalogItems_CategoryId` |
| widened | `Name` from max 60 to max 200 |

The single `InitialCreate` migration is regenerated with this schema, and the local database file is
deleted so the app builds it fresh. No other table changes: no order has ever referenced a category,
so no history moves.

## The contract

Both sides implement exactly these names. Nothing here is renamed, extended or improved by either
side alone. A change to this section is agreed first and told to everyone it touches.

### Routes

`GET /api/admin/categories`

```json
{ "categories": [
  { "categoryId": "guid", "name": "Bier", "colourHex": "#C62828", "sortOrder": 1, "isActive": true }
] }
```

Ordered by `sortOrder` ascending. Switched-off categories are included.

`POST /api/admin/categories` with `{ "name": "Kaffee", "colourHex": "#6D4C41" }`
returns `201` and one category object in the shape above. The new category takes the last position.

`PUT /api/admin/categories/{categoryId}` with `{ "name": "Kaffee", "colourHex": "#6D4C41" }`
returns `200` and the category object.

`POST /api/admin/categories/{categoryId}/move` with `{ "direction": "up" }` or `{ "direction": "down" }`
returns `200` and the full list in the `GET` shape, so no client recomputes positions. Moving the
first one up or the last one down is accepted and changes nothing.

`POST /api/admin/categories/{categoryId}/activate` returns `200` and the category object.

`POST /api/admin/categories/{categoryId}/deactivate` returns `200` and the category object, or the
refusal below when active articles still point at it.

`GET /api/admin/items` keeps its route and returns items carrying `categoryId` only. The admin page
reads names, colours and positions from `GET /api/admin/categories`, so no value is served twice.

`POST /api/admin/items` and `PUT /api/admin/items/{itemId}` take `categoryId` (Guid) where they took
`categoryName`. The field `categoryName` is gone from both the request and the item view.

`GET /api/catalog`, which the phone fetches, returns

```json
{ "categories": [ { "categoryId": "guid", "name": "Bier", "colourHex": "#C62828", "sortOrder": 1 } ],
  "items": [ { "itemId": "guid", "categoryId": "guid", "name": "Bier Gross", "priceCents": 400,
               "sortOrder": 1, "isAvailable": true, "productionMinutes": null } ] }
```

Only active categories and active articles appear. Categories are ordered by `sortOrder`.

### Error message keys

Returned by the backend in the problem body as `messageKey`, and used unchanged as the localization
key on the frontend.

| Key | When |
|---|---|
| `admin.categoryNameMissing` | the name is blank |
| `admin.categoryNameTaken` | another category already has that name |
| `admin.categoryColourInvalid` | the colour is not `#RRGGBB` |
| `admin.categoryHasActiveItems` | switching off is refused because active articles point at it |
| `admin.itemCategoryUnknown` | an article is saved with a category that does not exist |
| `admin.itemCategoryIsOff` | an article is saved into, or reactivated in, a switched-off category |

`admin.itemCategoryMissing` is deleted, backend and both locale files, because an article now carries
a category id rather than typed text.

### Frontend types

`core/apiTypes.ts` carries `CatalogCategory { categoryId, name, colourHex, sortOrder }` for the phone
and `AdminCategory { categoryId, name, colourHex, sortOrder, isActive }` for the laptop.
`CatalogItem` and `AdminItem` carry `categoryId` and no longer carry `categoryName`.

## What is deleted

Per rule 17, in the same change: the `CategoryName` property, its EF configuration and its column;
`SaveItemRequest.CategoryName` and `AdminItemView.CategoryName`; the derived category list on the
server (`Min(item.SortOrder)`) and the alphabetical sort on the client; `categoryNames` on the admin
items store; the free-text combobox in the article form; `admin.itemCategoryMissing` in both locale
files; and every test that asserted the old grouping or ordering.

## Testing

Backend, unit and integration: the refusal to switch off a category with active articles, the refusal
to reactivate an article under a switched-off category, name uniqueness, colour format, position
after create, position after move up and move down at both ends, the catalog omitting switched-off
categories and their articles.

Frontend: the category headings carrying their controls, creating a category from the list and from
the article dialog, the refusal messages appearing in the operator's language, and the ordering coming
from the server rather than from an alphabetical sort.
